## 1.5.7（就诊接事件协议）

- 治病前先向终端交提案：`event_type=medical_treat`、`event_id=med-<病>-<起始时间>`、金额/理由/病情都在 payload 里。
- 终端返回 `deny`/`defer` 就不扣款、不治疗（比如群聊资金暂缓）；返回 `duplicate` 仍继续（扣款本身幂等，说明上次已批）。
- 扣款后必发回执：成功 `success`、失败 `fail`（带 `code`/`reason`/`balance`），回执异常不影响治疗。
- 老终端没有 `submit_event` 时自动按原流程走，不会把看病卡死。
- 测试：新增 7 条（放行/驳回/重复/失败回执/老终端/回执异常），全量 45 条通过。

## 1.1.3（面板读不到数据的真正原因）

- 根因：AstrBot 把 `bridge-sdk.js` 注入在 `app.js` **之后**（实测页面里 56 行是 app.js、
  57 行才是 SDK）。这三个面板在脚本开头就 `const bridge = window.AstrBotPluginView`，
  那一刻全局还不存在，于是 `bridge` 永远是 `null`——所有 `get()` 都返回空，
  面板自然「读取不到」，而语音面板是每次调用重新找桥接，所以它一直正常；
- 改成：每次请求都 `resolveBridge()` 重新解析；启动时 `waitForBridge()` 最多等 6 秒再加载；
- 用 Node 模拟「先执行脚本、后注入 SDK」验证：注入前返回 null 不抛错，注入后正常拿到数据。

## 1.0.0

## 核心：治病前先要钱

```
医疗算出要花 2400
  → 上报终端（Amo）
  → 终端下发金融扣款 + 数据记账
  → 扣到了？执行治疗 : 不治疗，病情继续加重
```

医疗自己**不碰钱**。它只负责「这病怎么治、多少钱、医保报多少」，钱由终端统一调度——
这样每一笔账她都知情，不会出现"医疗偷偷划钱、Amo 不知道"的情况。

## 病情分级

| 病 | 严重度 | 治疗费 | 医保 | 不治会变成 |
|---|---|---|---|---|
| 过度疲劳 | 轻 | 0（休息） | — | — |
| 轻微不适 | 轻 | 30–80 | 门诊 | 感冒 |
| 感冒 | 轻 | 150–300 | 门诊 | 发烧 |
| 发烧 | 中 | 300–600 | 门诊 | 肠胃炎 |
| 肠胃炎 | 中 | 800–1500 | 门诊 | 阑尾炎 |
| 阑尾炎 | 重 | 8000–15000 | 住院 | — |
| 骨折 | 重 | 6000–20000 | 住院 | — |

## 医保

- 门诊：起付 300，报 70%；
- 住院：起付 1500，报 85%；
- 大病：超过 2 万的部分再报 60%；
- 年度上限 30 万。

所以阑尾炎 12000 的实际自付是 **3075**，不是 12000。这就是「有医保的人不会因为一场手术破产」的真实感。

## 会硬扛

小病有概率先不去——余额越紧张越可能扛。这比「一生病就去医院」像人。

拖着不治，病情会升级：轻微不适 → 感冒 → 发烧 → 肠胃炎 → 阑尾炎。

## 给终端用的接口

| 方法 | 说明 |
|---|---|
| `status()` | 当前状态（会自动处理自愈） |
| `fall_sick(key)` | 让她生病，key 留空按常见病抽 |
| `quote()` | 报价：总费、医保报、自付 |
| `treat()` | 完整流程：报价 → 请终端扣款 → 治疗或放弃 |
| `worsen()` | 病情加重一档 |
| `heal()` | 直接治好（管理员用） |

## 配置

| 项 | 默认 | 说明 |
|---|---|---|
| `sick_prob` | 0.02 | 基础生病概率（雨天 +0.03，低温 +0.02） |
| `auto_treat` | 是 | 生病后要不要自动去治 |
| `tough_it_out` | 是 | 小病先扛着 |
| `insurance_enable` | 是 | 关掉就全额自费 |
| `worsen_enable` | 是 | 不治会变重 |
